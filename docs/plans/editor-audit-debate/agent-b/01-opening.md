# Position B Opening: Targeted Hot-Path and Correctness Fixes Only

Position B argues that engineering effort should focus exclusively on verified correctness hazards and high-frequency per-frame/per-edit bottlenecks, delivered as small, independent PRs with rigorous tests or benchmarks. Wide architectural sweeps and speculative memoization should be rejected or deferred.

### B1. Web offscreen rendering has an active concurrency race that risks GPU corruption (Criteria: C1, C2, C3)
The audit correctly identifies that [`drawOffscreen.web.ts`](file:///Users/nverk/Dev/tuck/src/editor/render/drawOffscreen.web.ts#L16-L58) shares a single module-level `shared` WebGL surface across asynchronous gaps: `await drawAsPicture` (L32) and `await snapshot.makeRasterImage()` (L48). While [`markThumbnail.tsx`](file:///Users/nverk/Dev/tuck/src/editor/render/markThumbnail.tsx#L19-L42) serializes its own renders with a local `queue`, concurrent callers in [`renderDocument.tsx`](file:///Users/nverk/Dev/tuck/src/editor/render/renderDocument.tsx#L83) (L83, L98, L118), [`cutMask.tsx`](file:///Users/nverk/Dev/tuck/src/editor/tools/cut/cutMask.tsx#L72) (L72, L76, L80), and [`useRenderedDocument.tsx`](file:///Users/nverk/Dev/tuck/src/screens/export/useRenderedDocument.tsx#L54) bypass it entirely. If a mark thumbnail runs alongside Cut or export, `surfaceFor` can invoke `shared?.free()` (L73)—destroying the underlying WebGL context via `loseContext()` and `deleteContext` (L98–L99)—while another caller awaits readback. Moving serialization inside `drawOffscreen.web.ts` and removing the duplicate queue in `markThumbnail.tsx` is an urgent correctness fix. (Note: the audit misstated that `sampleColor.ts` calls this; no such file exists).

### B2. Preserving stroke identity eliminates $O(N^2)$ Skia path rebuilding (Criteria: C1, C2, C3)
In [`strokes.ts`](file:///Users/nverk/Dev/tuck/src/editor/layers/strokes.ts#L114-L134), `addStroke` invokes `recenterDrawing` (L91–L108) on every committed stroke. Whenever the bounding box center shifts by $\ge 0.01\text{px}$, `recenterDrawing` maps all existing strokes into newly allocated objects and point arrays (L101–L106). In [`DrawingLayerView.tsx`](file:///Users/nverk/Dev/tuck/src/editor/layers/drawing/DrawingLayerView.tsx#L60-L69), compiled `SkPath`s are cached in `WeakMap<MaskStroke, SkPath>` keyed strictly by stroke identity (`pathFor`). Because every stroke's identity is destroyed on every addition, the cache misses completely: adding the 50th stroke forces Skia to rebuild all 49 prior paths from scratch. Keeping stroke coordinates stable (or offsetting cached paths) eliminates this quadratic degradation in pure TypeScript without touching Skia layer invariants.

### B3. Live overlay optimizations target the real 60/120fps frame budget (Criteria: C1, C2)
Frame drops occur during user gestures, where the audit's findings are acute:
1. **Live Redaction:** In [`LiveStrokeOverlay.tsx`](file:///Users/nverk/Dev/tuck/src/editor/canvas/LiveStrokeOverlay.tsx#L443-L476), `LiveRedactionStrokes` calls `recordRedactionStrokes` on every pointer move with `bounds = null`. In [`RedactionLayerView.tsx`](file:///Users/nverk/Dev/tuck/src/editor/layers/redaction/RedactionLayerView.tsx#L285-L294), this forces `saveLayer` with unbounded extent (`-UNBOUNDED = -1_000_000`) and rebuilds the entire filter graph and all prior marks on every touch event. Pre-recording existing marks and passing document bounds saves critical GPU cycles.
2. **Stroke Eraser Overkill:** [`StrokeErasedDrawing`](file:///Users/nverk/Dev/tuck/src/editor/canvas/LiveStrokeOverlay.tsx#L268-L323) mounts a separate `<DimmedStroke>` (L309–L323) with its own `useDerivedValue` and `<Group>` for *every single stroke* in every layer, evaluating array inclusion per-frame. Batching strokes into hit vs. unhit groups eliminates hundreds of mounted worklets.
3. **Worklet Hit-Testing:** [`strokesHitBy`](file:///Users/nverk/Dev/tuck/src/editor/layers/strokes.ts#L332-L355) is called on the UI thread during eraser swipes ([`useToolStroke.ts`](file:///Users/nverk/Dev/tuck/src/editor/canvas/useToolStroke.ts#L238)) without checking AABB bounds first, repeatedly computing segment distances on strokes far away from the pointer.

### B4. Precomputing bounds in `drawingPieces` removes an algorithmic $O(P^2)$ hotspot (Criteria: C1, C2, C5)
In [`drawingEdits.ts`](file:///Users/nverk/Dev/tuck/src/editor/layers/drawing/drawingEdits.ts#L336-L366), `drawingPieces` iterates over all pairs of pen strokes. For each pair, `inkTouches` (L305–L324) repeatedly recomputes `strokeBounds` (L309–L310) by walking all points of both strokes. Precomputing bounding boxes once per stroke ($O(P)$) before pairwise comparison ($O(P^2)$) yields an immediate, easily tested pure-logic speedup.

### B5. The `Editor.tsx` memoization sweep is illusory optimization (Criteria: C1, C3, C5)
The audit criticizes unstable references in [`Editor.tsx`](file:///Users/nverk/Dev/tuck/src/editor/Editor.tsx#L238-L527). However, there is **not a single `React.memo` in `src/editor/`**. In standard React, stabilizing `view`, `toolStarters`, or `editorContext` does *not* prevent child components (`EditorCanvas`, `Dock`, `Rail`) from re-rendering when `Editor` updates. Gating tool hooks is also largely moot: `useAdjustTool.ts` (L81–L86) only syncs when adjustments change, and `useCropTool.ts` (L68–L71) memoizes `photoSize`. A broad memoization overhaul introduces brittle dependency arrays and high regression risk for zero measurable frame savings.

### B6. ToolSpec generalization and P2 polish add churn without runtime wins (Criteria: C3, C4, C5)
Refactoring `ToolSpec` to absorb Cut/RemoveBG routing touches core tool contracts ([`defineTool.ts`](file:///Users/nverk/Dev/tuck/src/editor/defineTool.ts), [`builtInSpecs.ts`](file:///Users/nverk/Dev/tuck/src/editor/builtInSpecs.ts), [`useEditorTools.ts`](file:///Users/nverk/Dev/tuck/src/editor/useEditorTools.ts)) without touching any hot path. Similarly, `Dial.tsx` tick rendering (L212–L220), `TextStylePanel.tsx` HSV duplication (L140–L275), and `sameDocument` stringification are trivial outside gesture loops. They should remain in the backlog, not inflate high-risk refactor PRs.

## Known Weaknesses
Position B deliberately preserves code duplication in non-hot paths: the three polyline walkers (`segmentsNear`, `alongLine`, `eachAlong`) and HSV math in `TextStylePanel.tsx` remain unmerged. It also accepts that root `Editor.tsx` components will continue re-rendering during state changes, prioritizing stability and surgical PR reviewability over theoretical component purity.
